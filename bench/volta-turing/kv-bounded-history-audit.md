# Bounded KV history staging: implementation boundary

2026-10-24, source audit and test-only GPU partial-attention hook. The model stayed unloaded to preserve host RAM. TODO 8.3 remains open.

The streamed target prefill path allocates one K/V staging pool for every logical page of a QSA layer (`take_stage`, `src/prefill/prefill.cpp`). Before attention, `kv_stage_from_host` copies the layer's entire prior prefix `[0, p0)` into that identity-mapped pool. The chunk's new rows are also appended there. The prompt attention kernels read selected cell IDs through that page table and return normalized FP32 outputs. K8V4 stays encoded in the staging pool and is dequantized at gather; the draft's own state is INT8 in its window-sized ring.

A smaller staging pool cannot simply reuse the current identity page table: selected pages outside the pool would point past it. A page-window implementation needs a remapped table or selected-ID translation, copy/compute fences before reusing each window, and an attention partial for every selection slice. The current prompt attention API returns only the normalized result. Correctly combining slices needs each partial's maximum score, exponential sum (or log-sum-exp), and weighted value sum. Averaging normalized outputs or merging them with slice lengths changes attention. The merge must also handle empty slices, the last partial page, selections crossing a page boundary, query-dependent widths, and a window that ends exactly at the draft's attention cutoff.

The first implementation gate is a test-only partial-attention API plus a GPU parity harness that compares the merged result with unsliced attention for FP16 and encoded K8V4 pools, including those boundaries. The next gate is to move the bounded page plan into production prefill with copy/compute fences and an explicit VRAM cap. Only then can a whole-model ABBA compare output quality, prefill/decode speed, PCIe bytes and expert slots against the current full-prefix staging. The existing stage and dispatch remain in place.

Baseline boundary checks on RTX 2060 SUPER: the existing unsliced K8V4 `qsa_prompt_attn_parity` harness passed `QA_EMPTY=1 QA_GRAPH=1` at context 2,048 with 32 queries, and `QA_EMPTY=1` at context 2,049 with 33 queries (a partial final page). The new-kernel error versus its FP64 reference was 5.72e-6 and 6.33e-6 respectively. These checks establish current empty/partial-page behavior; they do not test bounded staging or LSE merging. Single-run timing was 1.067/1.042 ms per chunk and is not a speedup claim.

The CUDA FP16/K8V4 partial-attention hook exposes per-query/head base-2 log-sum-exp alongside the existing normalized output. It uses the current v1 prompt kernel's online max and sum; an empty selection emits `-inf` and zero. The ordinary call passes a null LSE pointer. `QA_WINDOW_MERGE=1` splits each test selection into two slices (empty-first, empty-second, or half, depending on query), runs both through the hook, and combines normalized outputs with `exp2(lse - max)` weights. This tests the merge math against the unsliced GPU output; it does not stage or remap any K/V pages.

On RTX 2060 SUPER, `QA_EMPTY=1 QA_GRAPH=1 QA_WINDOW_MERGE=1` at context 2,049/33 queries passed with maximum merged-versus-unsliced K8V4 difference 2.76e-6 (output scale 6.12). A sparse 32,768/32-query run also passed at 2.76e-6 (scale 6.87). The original unsliced 2,048/32-query `QA_EMPTY=1 QA_GRAPH=1` output hash stayed `e8e461e5cfee015b`. Targeted K8V4 CUDA memcheck reported zero errors and racecheck reported zero hazards at 2,049/33.

The same two-window hook now supports synthetic FP16 pools, the proposed draft-history format. At 2,049/33 with empty and partial-page boundaries, merged-versus-unsliced maximum difference was 9.00e-7 (output scale 2.84); at sparse 32,768/32 it was 1.21e-6 (scale 3.09). The ordinary FP16 output hash stayed `e4d79df06d7fd66e` with the test disabled. FP16 memcheck reported zero errors and racecheck zero hazards at 2,049/33. The changed translation unit compiled for sm70. Volta runtime and HIP compilation are unavailable here. The hook is CUDA sm75+ only, with no production caller or speedup claim. The live drafter still stores INT8, so this FP16 test is format math, not live draft quality.

`QA_BOUNDED_STAGE=N` now exercises a test-only N-page staging pool. The host planner collects selected logical pages from all queries, processes them in sorted N-page windows, remaps each page to a reusable slot, and filters each query's IDs to that window. It packs K, V and K scales from the harness's host arrays into bounded pinned bounce buffers, issues one host-to-GPU transfer per run, launches partial attention, and merges normalized outputs with LSE weights on the host. A device synchronization before each slot reuse makes this a correctness prototype; it does not overlap transfers with compute. The harness checks each query's total covered width and finite outputs. Its original full GPU pools remain allocated, so the test's process VRAM use does not equal the bounded pool's size.

For the sparse 32K case, the bounded pool holds 417,792 B of K8V4 or 1,048,576 B of FP16 KV, versus 26,738,688 B or 67,108,864 B for a full 32K identity pool. Those are pool-capacity calculations, not measured end-to-end memory savings. Targeted pinned-bounce CUDA memcheck at 2,049/8 reported zero errors for both formats. The wall time includes CPU packing, transfers, attention, result downloads and host merging; it is not comparable to the production prefill path or accepted-token speed. The production path still needs a GPU-side or batched planner, asynchronous copy/compute fencing, live draft INT8 handling, resource accounting and whole-model qualification before any adoption.
